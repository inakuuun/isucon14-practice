# Issue作成

## 目的

リポジトリの指示、資料、実装を確認し、優先度の高い課題を着手可能なIssueにする。

## 手順

1. 最初にルートの `AGENTS.md` を読み、その指示を優先する。ユーザーが示した資料も確認する。
2. 関連する実装、設定、仕様、計測結果を確認し、事実と仮説を分ける。
3. 効果、緊急度、実装範囲を基に優先順位を決め、独立した課題は分割する。
4. [テンプレート](references/issue-template.md)を使い、背景、作業、完了条件、確認方法、対象外、根拠を書く。

## スロークエリログからの作成

ユーザーがスロークエリログ（既定: `home/isucon/analysis/db/slow-query-dump.log`）を示した場合や、DBのボトルネックからIssueを作る場合は、[スロークエリ手順](references/slow-query.md)に従う。

- `# Profile` 表の Rank 1 から順に、1 Rank を1 Issueとして作成する。
- 各IssueにはQuery ID、Response time、Calls、Rows examine、リテラルを `?` にしたSQL、発行元のGo関数とエンドポイントを書く。
- 既存Issue・既存修正と重複するRankは作成せず、その旨を報告する。

## 原則

- 1 Issueは1回の変更で完了できる粒度にする。
- 完了条件は観測可能にし、維持すべき既存仕様を含める。
- 未確認の効果を断定しない。実行できない確認は後続作業として明示する。
- 根拠不足なら実装Issueではなく、成果物と判断基準を定めた調査Issueにする。
- 秘密情報や環境固有の接続情報を含めない。

## GitHubへの登録

既定では下書きだけを返す。ユーザーが登録を明示した場合に限り、対象リポジトリを確認し、`gh auth status` で認証状態を確認する。

- 認証済みの場合だけ、本文を一時ファイルへ保存し、`gh issue create --title "<title>" --body-file <body-file>` で作成する。
- 認証されていない場合は登録せず、ユーザーによる `gh auth login` が必要だと伝える。
- ラベル等は既存運用を確認できた場合だけ指定する。
- 登録後はIssue番号とURLを伝える。コマンドが失敗した場合は成功したと報告しない。
