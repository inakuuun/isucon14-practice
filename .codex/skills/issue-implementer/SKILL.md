# Issue実装

指定されたIssueだけを作業範囲とし、ベンチマーカーが検証する仕様を壊さずにボトルネックを1つ解消する。

## 前提

- ルートの `CLAUDE.md` / `AGENTS.md` を最初に読み、その指示をこのスキルより優先する。
- コミット、push、PR作成はユーザーが明示的に依頼した場合だけ行う（PRは `pr-creator` に従う）。
- 実装基準は [references/coding.md](references/coding.md) を正本とし、実装前に読む。

## 手順

1. `gh issue view <number-or-url> --json number,title,body,state,url,labels,comments` で、背景・計測結果・やること・受け入れ条件・対象外を確認する。tracking Issueがあれば前提Issueの完了も確認する。
2. `git status --short` と `git branch --show-current` で作業ツリーを確認する。
3. Issueに記載されたSQL・関数・エンドポイントを起点に、コード・スキーマ・初期化処理と、同じテーブルを読み書きする他の箇所を調査する。仕様はマニュアルやAPI定義で確認する。
4. 受け入れ条件を満たす最小範囲で変更する。
5. 静的確認を行い、完了報告する。

次の場合は推測で実装せず、ユーザーへ確認する。

- Issueがclosed、またはマージ済みの変更と重複している。
- 変更対象や受け入れ条件を特定できない。
- Issueの内容がリポジトリ規約やマニュアルと矛盾する。
- 調査Issueで実装の根拠が揃っていない（調査結果の報告を成果物とする）。

## 実装方針

- 対象外は実装しない。関連して見つけた課題は報告に留め、必要なら `issue-creator` で別Issue化を提案する。
- 既存コードのライブラリ、エラーハンドリング、命名に合わせ、新しい依存は極力追加しない。
- 秘密情報や環境固有の接続情報を追加しない。

## 確認

ビルドやベンチマークが禁止されていても、次の静的確認は行う。

- `git diff --check` と、利用可能ならフォーマッタ（例: `gofmt -l`）。
- 変更したSQL・インデックスとアプリケーションのクエリ（カラム名、`WHERE` / `ORDER BY`）が対応していること。
- 変更したテーブルを読み書きする全箇所に更新漏れがないこと。

実行できない確認（DB初期化、`EXPLAIN`、ベンチマーク等）は、未実施と理由を報告する。

## Git

- 未コミット変更を破棄・退避・上書きしない（`git reset --hard`、`git checkout --`、`git clean`、`git stash` を行わない）。同じファイルを編集する場合は共存できる最小変更にする。
- ブランチ作成は依頼時のみ行い、命名は既存運用に合わせる（例: `perf/issue-<number>-<短い英語の説明>`）。
- コミットを依頼された場合は、既存の書式に合わせて本文に `Refs #<number>` を含め、関係ファイルだけをステージングする。

## 完了報告

```markdown
Issue #<number>「<タイトル>」の実装を完了しました。

変更内容:
- <主要変更>（`<file>:<line>`）

受け入れ条件:
- [x] <満たした条件>
- [ ] <未確認の条件と理由>

確認:
- <実施した確認>: 結果
- <未実施の確認>: 未実施（理由）

補足:
- <残課題、効果計測で確認すべき点、別Issue化の提案>
```

完了できなかった場合は、到達点、ブロッカー、次に必要な判断を明記する。
