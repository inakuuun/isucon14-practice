# Pull Request作成

現在のブランチがベースブランチへ加える変更を、レビュー担当者が目的、実装、検証状況、残存リスクまで判断できるpull request（PR）としてまとめる。リポジトリ固有の規約を最優先し、言語、ディレクトリ、検証コマンド、本文テンプレートを固定的に仮定しない。

## 権限の境界

- 差分の調査とPR文面の作成は行う。
- `gh pr create`、`gh pr edit`、pushなど外部状態を変える操作は、ユーザーがその操作を明示的に依頼した場合だけ行う。「PRを作成して」はGitHub上での作成依頼として扱い、「PR本文を作成して」「下書きを作って」は文面作成だけとして扱う。
- コミット、push、ブランチ作成をPR作成の前提として勝手に行わない。これらが必要な場合は、対象、ブランチ名、コミット内容、push先を含む具体的な準備手順を提案し、ユーザーの確認を得てから実行する。
- ユーザーが確認した準備手順の範囲では、ブランチ作成、選択したファイルのステージング、コミット、pushを順に実行してよい。確認された範囲を超える変更や、issueの変更、既存PRの更新は行わない。
- 未コミットの変更はユーザーの作業として保持する。PRに含まれないため、コミット済み差分と混同しない。

## 1. リポジトリ規約を確認する

作業対象に適用される `AGENTS.md` と、リポジトリ内のREADME、CONTRIBUTING、PRテンプレートなどを読む。そこから次を特定する。

- 許可・禁止されている操作
- 実装言語とプロジェクト構成
- 実行可能な検証と、実行してはならない検証
- PRの言語、書式、粒度
- 参照必須の仕様や設計資料

規約に外部資料の参照が指定されていれば、必要な範囲を確認する。一般的な慣例よりリポジトリ規約を優先する。



## 2. 比較範囲を確定する

最初に、作業ツリー、現在ブランチ、remoteを読み取り専用で確認する。

```bash
git status --short
git branch --show-current
git remote -v
```

ベースブランチは、ユーザー指定、既存PR、remoteの既定ブランチ、リポジトリ設定の順で根拠を探す。`main`、`master`、`develop` のいずれかと決め打ちしない。判定できなければ推測でPRを作成せず、候補と不足情報を伝える。

ベースが確定したら、原則としてthree-dot差分でPRに入る変更を確認する。

```bash
git merge-base HEAD <base>
git log --oneline <base>..HEAD
git diff --stat <base>...HEAD
git diff --name-status <base>...HEAD
git diff <base>...HEAD
```

必要に応じてコミット本文、rename、submodule、生成物、バイナリ差分も確認する。現在ブランチがベース自身、履歴が存在しない、または差分が空なら、PRを作れる状態ではないことを報告する。

`git fetch` はネットワークアクセスであり、リポジトリ規約とユーザーの許可範囲に反しない場合だけ行う。取得できない場合は、ローカル参照の鮮度が未確認であることを明示する。

### PR作成の準備が不足している場合

現在ブランチがベースブランチ自身、対象変更が未コミット、またはheadブランチが未pushである場合は、PRを作れないと報告するだけで終了しない。PRの目的と作業ツリーを踏まえ、必要な準備を次の粒度で提案する。

- 作成または使用するheadブランチ名
- ステージングとコミットの対象ファイル。無関係な変更や未追跡ファイルは明確に除外する
- コミットメッセージ
- pushするremoteとheadブランチ
- PR作成まで続けるかどうか

提案後、ブランチ作成、コミット、pushなど実際の変更操作へ進む前にユーザーへ明示的に確認する。ユーザーが確認したら、直前に作業ツリーを再確認し、合意したファイルだけを明示指定してステージングする。予期しない差分や競合を検出した場合は停止して状況を伝える。

## 3. 変更の意図と影響を理解する

ファイル一覧だけで要約せず、主要な差分とその呼び出し元・設定・スキーマ・仕様を読む。コミットメッセージは手掛かりとして使うが、実際の差分を優先する。

確認する観点:

- 変更前の問題と、変更後にどう改善するか
- 利用者や運用者から見た振る舞いの変化
- API、DB、設定、互換性、性能、セキュリティへの影響
- 今回意図的に対象外とした事項
- レビューで重点的に確認すべき仮定やリスク

性能改善では、計測していない効果を断定しない。差分から説明できる仕組み上の改善と、未実施の性能計測を分けて記載する。リポジトリ規約で性能計測が禁止または対象外なら、必要に応じて「未実施（リポジトリ規約により対象外）」とする。

## 4. issueと既存PRを扱う

ブランチ名、コミット、ユーザー入力、PRテンプレートから関連issueを特定する。GitHubへ読み取りアクセスでき、必要な場合は `gh issue view` や `gh pr view` で本文、受け入れ条件、既存メタデータを確認する。

- issueを完全に解決する根拠がある場合だけ `Closes #<number>` を使う。
- 一部対応や参照だけなら `Refs #<number>` を使う。
- 関連issueが確認できなければ、番号を推測しない。該当セクションを省くか「なし」「未確認」と明記する。
- 既存PRを更新する場合は、既存の有用な説明、チェックリスト、リンクを保持する。

## 5. 検証状況を整理する

検証コマンドはリポジトリ規約、変更対象のビルドシステム、既存スクリプトから選ぶ。特定のエコシステムを仮定しない。ユーザーがすでに実施した結果と、自分が確認した結果を区別する。

実行を許可されていない検証は実行しない。静的確認だけが許可される場合は、差分レビュー、参照検索、構文上の整合性など実際に行った確認を具体的に記す。未実施項目は理由を添え、成功したように表現しない。

## 6. タイトルと本文を書く

リポジトリのPRテンプレートがあれば、それを優先する。指定がなければ、リポジトリで主に使われている言語で簡潔に書く。タイトルは実装手段の列挙ではなく、主要な変更と目的が分かる一文にする。

PRのタイトルまたは本文を作成するときは、[references/pr-body-template.md](references/pr-body-template.md) を読む。リポジトリ固有のPRテンプレートがある場合はそちらを優先し、参照ファイルは不足する観点を補うために使う。

## 7. 提示またはGitHub上に作成する

文面作成だけなら、タイトル、本文、比較したベースとhead、検証状況、判断できなかった事項を提示する。

GitHub上での作成を明示的に依頼されたものの、ブランチ作成、コミット、pushが未実施の場合は、「PR作成の準備が不足している場合」に従って必要な操作を提案する。ユーザーの確認後に準備を実行し、そのままPR作成まで進める。準備操作の途中で失敗した場合は、成功した地点と残作業を報告し、未完了の操作を成功したと扱わない。

作成直前に次を再確認する。

- ベースとheadが正しい
- `<base>..HEAD` にPR対象のコミットがある
- 未コミット変更をPR内容として記載していない
- タイトルと本文が実際の差分に一致する
- issueの自動クローズ表現が妥当である
- 必須検証の結果または未実施理由が記載されている

認証状態を確認し、一時ファイル経由など安全な方法で本文を渡す。

```bash
gh auth status
gh pr create --base <base> --head <head> --title "<title>" --body-file <body-file>
```

作成後はPR番号とURL、タイトル、ベース/head、検証結果を報告する。コマンドが失敗した場合はエラーと再実行に必要な条件を伝え、成功したとは報告しない。

## 安全上の注意

- `git reset --hard`、`git checkout --`、`git clean` などでユーザーの変更を破棄しない。
- secret、認証情報、個人情報、巨大なログ、生成物を本文へ転載しない。
- PRの範囲を超える修正や履歴の書き換えを勝手に行わない。
- 外部アクセスや検証が規約で禁止されている場合、PR作成のために例外扱いしない。
