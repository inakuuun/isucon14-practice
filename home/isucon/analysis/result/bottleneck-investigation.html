P0 複合インデックス

-- chairs
UNIQUE KEY idx_chairs_access_token (access_token),
KEY idx_chairs_owner_id (owner_id)

-- chair_locations
KEY idx_chair_locations_chair_id_created_at (chair_id, created_at)

-- rides
KEY idx_rides_chair_id_updated_at (chair_id, updated_at),
KEY idx_rides_chair_id_created_at (chair_id, created_at),
KEY idx_rides_user_id_created_at (user_id, created_at)

-- ride_statuses
KEY idx_ride_statuses_ride_id_created_at (ride_id, created_at)

app_sent_at と chair_sent_at は初手の索引に含めない。まず ride_id で最大6状態まで限定し、通知済み時刻更新による索引更新コストを避ける。

P0 owner/chairs の集計範囲を限定

先に対象オーナーの椅子を抽出し、その椅子の chair_locations だけへ LAG を適用する。

P0 通知処理のN+1を解消

getChairStats は椅子の全ライドを取得後、ライドごとに状態履歴を読む。完了ライド数と評価平均を単一集約SQLへ置き換える。ポーリング間隔30msの変更は原因修正と再計測の後に検討する。

P1 nearby-chairs を一括取得

アクティブな椅子、未完了ライドの有無、最新位置、マンハッタン距離を一括クエリで判定し、椅子数・ライド数に比例するSQLループをなくす。

確認 評価APIの4xx

生アクセスログで 400/404/409/499 のどれかを特定し、アプリケーションログと突き合わせる。

推奨実施順と再計測

  1. 1-schema.sql にP0インデックスを追加。
  2. owner/chairs の距離集計を対象オーナーに限定。
  3. getChairStats を単一集約クエリへ変更。
  4. nearby-chairs のN+1を一括クエリへ変更。
  5. 許可された環境で再計測し、通知頻度、座標更新、評価APIを再評価。

  • レスポンスの距離、評価平均、近隣椅子の可用性判定が従来と一致すること。
  • 通知状態が発生順に最低1回返ること。
  • owner/chairs、nearby-chairs のP95と通知系の累積時間が低下すること。
